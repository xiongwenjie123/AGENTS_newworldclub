00 产品总览 & 世界观叙事

 

00.1 产品名称

 

- 中文：新大陆俱乐部

- 英文：New World Club，缩写 NWC

- 产品定位：人类星际协作操作系统 Human Expedition Operating System

 

赛道定位（比赛）：未定信号赛道，招聘校准方向高阶变体，基于用户私有协作航行档案，完成复杂创新使命的人机协同编组平台。

商业定位（赛后）：面向创新团队、开源社区、科研项目、社会创新组织的人机协同协作基础设施。

 

00.2 核心Slogan

 

不是寻找最优秀的人，而是寻找可以共同完成伟大航行的互补个体。

AI让星舰跑得更快，人类决定星舰驶向何方。

 

00.3 完整世界观（产品内全部文案、NPC对话、页面叙事全部来源于此）

 

历史：1493年大西洋风暴，哥伦布船队。船长无法掌控风暴，舵手无法决定目的地，水手不能做战略，瞭望员无法修船；每一个岗位各司其职，所有人的行动指向同一个航向，船队才得以幸存。

现在：人类进入AI时代，我们寻找的不再仅仅是地理新大陆，而是八种新大陆：新知识、新职业、新组织、新文明、新生产方式、新社会结构、新人机协作方式、新经济运行方式。

隐喻：每一次复杂创新使命，就是一次星际远航；项目团队就是一艘星舰；参与者不是求职者，而是登舰舰员；简历是自我宣传，航行档案是真实协作行为沉淀的私有资产；舰载智能Ship Intelligence是星舰AI算力系统，它增强人类，但永远不能替代人类对使命的价值判断。

核心概念：

 

- 登舰：用户申请加入协作网络，完成登舰测试，获得地球文明编号 NW‑XXXX

- 航行档案（Expedition Passport）：用户核心私有数据资产，本产品的护城河

- 21席 21 Seats：21种复杂使命所必需的认知功能席位，≠职业、≠岗位招聘；分为探索舱、建造舱、治理舱，每舱7席。

- 舰队Expedition Formation：针对一个Mission使命，由系统基于航行档案匹配生成的互补协作单元；21席是职能全集，允许单人兼任多席，允许舰载智能临时补位部分执行席位，治理舱决策、守门、风险席位必须由真人担任。

- Mission航行使命：复杂创新任务，固定闭环：提出 → 指引 → 拆解 → 执行 → 监督 → 决策 → 审核

- 舰载智能 Ship Intelligence：Agent集群，多Agent协同，不掌握使命决策权；输出全部需要人类确认。

- APU AI生产力单元：商业V1.0概念，一个由【人‑能力‑Agent‑算力‑数据‑场景】组成的生产单元；黑客松MVP仅保留数据模型，不实现真实经济闭环。

- APU Credit新大陆生产力凭证：用户协作贡献的实验性信用积分；MVP仅本地模拟，无金融属性。

 

00.4 赛道四大自检标准答案（写入系统文档、海报、Innovate Trace航迹）

 

1. 真实问题：复杂创新使命场景下，现有组队工具依赖简历、自我标签；简历是主观自我描述，无法表征人的认知模式、风险偏好、历史协作表现；团队经常出现技能齐全，但认知职能席位缺失，项目失败，大量人力沉没。目标用户：创新使命参与者、开源协作成员、社会创新项目团队。

2. 独有数据：用户私有航行档案，包含①登舰测试原始开放式作答、推理路径；②每一次Mission完成回填的真实协作表现、席位产出、反馈记录；该数据集仅属于该用户，外部无法获取；持续积累，越用越独特。

3. 个体差异：更换一份用户完整航行档案，同一Mission、同一候选池，系统输出的21席画像、舰队编组方案发生实质性改变。路演必须做对照实验。

4. 长期价值：持续使用，用户沉淀不可替代的航行护照；包含历次使命的真实协作证据，离开本系统，全部协作证据资产丢失，需要重新证明自身协作能力。

 

00.5 两道“去掉测试”（产品设计必须满足）

 

1. 去掉私有航行档案数据：系统退化为一套通用情景心理问卷，无法输出个性化21席画像、无法完成定制化组舰。

2. 去掉AI舰载智能：人工处理几十位候选者的开放式文本解析、多维度能力评估、互补舰队编组，人力成本极高，无法规模化。

 

 

 

01 业务目标、版本划分、范围边界

 

1.1 版本分支定义（代码仓库两个主分支，AtomCode严格区分）

 

分支A： mvp‑hackathon 【比赛MVP，48小时交付，部署魔搭创空间】

 

目标：完整跑通赛道要求Demo闭环，满足中客松全部提交要求；不做完整多端App、不做真实金融、不做大规模用户、不做实时多人协同。

支持平台：PC Web + H5移动端自适应；

砍掉：安卓/iOS原生App、微信小程序、完整中台后台、大规模多用户实时协同、真实TTS‑NPC完整游戏化；仅保留TTS文字转语音Demo样例；APU Credit仅为数据库字段模拟；

必须实现核心闭环：

 申请登舰 → 登舰情景测试(开放式问答，AI解析) → 生成初始化航行档案&21席画像 → 候选池管理 → AI组舰算法（支持两套档案对照演示） → 舰桥工作台Mission可视化 → 舰载智能Agent模拟 → Mission模拟完成，回填航行档案 → 航行护照查看 

 

分支B： commercial‑v1 【商业完整版本，赛后迭代】

 

目标：完整可商用产品，全端覆盖，完整中台后台，完整游戏化NPC语音交互，完整APU生产力单元骨架、组织权限体系、企业租户模式。

支持平台：PC Web、H5自适应、微信小程序、安卓原生App、iOS原生App。

在MVP全部功能基础上增加：多租户组织、完整权限中台、NPC对话交互、完整TTS语音、消息推送、实时多人协同工作台、贡献信用系统、APU生产力单元管理、运营后台、数据分析看板。

 

1.2 不在本期实现（无论MVP/Commercial V1）

 

1. 区块链、代币、加密货币、真实融资信贷；APU Credit仅做系统内贡献积分，不与法币打通。

2. 大规模百万用户高并发（架构预留扩展，第一版目标支持数千用户）。

3. 真实第三方算力采购、硬件调度；仅做业务模型，不对接GPU硬件底层。

 

1.3 交付给比赛的产出（mvp‑hackathon分支输出物）

 

1. 可访问Web Demo链接（魔搭创空间部署，Running状态）

2. ≥2分钟演示视频，包含两套航行档案对照演示

3. 竖版项目海报80×180cm（4:9）

4. Innovate Trace航迹文档（问题/数据/验证/迭代）

2.2 用户画像

 

画像A：创新项目参与者（核心用户）

 

22‑40岁；黑客松选手、开源贡献者、社会创新项目成员、科研项目成员；需要组队完成复杂创新任务；厌烦只靠简历、标签的传统组队；希望找到认知互补的伙伴；希望沉淀自己真实的协作证据，而不是一份美化简历。

 

画像B：使命发起者（舰队指挥官）

 

创新项目负责人、实验室负责人、项目发起人；手上拥有复杂Mission；很难评估候选人真实协作能力；希望系统辅助自己组建平衡的协作团队；需要记录项目中每个人的真实表现。

 

画像C：平台运营人员（商业版本）

 

平台运营，维护登舰测试题库，维护Mission模板，查看平台整体航行数据统计，处理用户申诉。

 

2.3 用户非功能性诉求

 

1. 隐私：我的航行档案属于我本人，我可以授权谁查看我的哪些数据，可以随时导出全部个人数据。

2. 可解释：AI输出的21席得分、组舰建议，必须给出依据，不是黑盒；每一项分数要溯源：来自哪几道登舰测试回答、哪几次历史Mission反馈。

3. 可控：AI所有建议均可以人工否决、人工修改；组舰算法输出只是建议，指挥官可以手动调整舰队人员。

C --> D[系统更新用户航行护照；增加一条Mission航行记录，授予星标；用户称号可以升级Explorer → Navigator → Pathfinder → World‑Builder]

D --> E[生成本Mission完整航行报告，归档；Innovate Trace过程文档自动归档]

E --> F[舰员可以带着更新后的航行档案，参与下一次Mission]

 

 

⚠️业务规则：航行档案是时序版本化存储，不能覆盖历史记录；每一次回填产生新的版本快照，可以回溯历次变化；这是赛道“未定信号”个体差异的数据源根基。

 

3.5 旅程5｜老用户再次参与Mission

 

用户已经拥有经过1次/多次Mission回填后的航行档案；再次进入候选池；组舰算法读取已经迭代后的私有航行档案，输出和初始化完全不同的匹配结果；越多次航行，画像越贴近真实的协作行为。

 

3.6 旅程6｜【路演Demo对照演示专用旅程｜mvp‑hackathon分支核心】

 

该流程是比赛评委打分核心，系统必须专门支持“快速切换两套模拟脱敏航行档案”的演示模式，内置两套预置测试数据集： User‑Alpha 、 User‑Beta ，两套画像完全相反。

 

1. 加载预置候选池，候选池包含 User‑Alpha（高探索，极低风险守护）；其余候选人员固定不变；Mission固定为「探索AI时代新型社区经济模型」

2. 运行AI组舰算法；输出舰队结果，截图记录；Alpha分配至探索舱探索者席位；治理舱风险岗位由其他人补齐。

3. 仅把候选池中的User‑Alpha替换为预置User‑Beta（高风险守护，低探索）；Mission不变、其余候选人员全部不变；重新运行组舰算法

4. 观察输出：Beta被分配治理舱风险官、守门人席位；探索舱需要重新从剩余候选挑选人选；整套舰队席位分配发生实质改变。

5. 演示完成：选择其中一支模拟舰队，进入舰桥工作台，演示舰载智能Agent；模拟Mission完成，执行反馈回填，展示同一个用户航行档案版本变化。

 

系统开发要求：MVP需要做一个【演示模式开关】，一键切换预置数据集，减少路演现场操作失误。

05 八大业务系统完整需求规格

 

完全沿用原始设计八大系统；区分MVP实现范围 / Commercial‑V1增强范围。

 

System‑01：登舰测试系统

 

定位：采集用户独有的开放式情景作答原始数据，作为初始化航行档案的输入源；注意：测试只是初始化，真正壁垒来自后续Mission回填。

 

功能需求

 

1. 测试引导页：世界观叙事，说明测试不是考试，没有对错，采集你的真实决策逻辑。

2. 情景问答题库：开放式自由文本输入，不是选择题。

- MVP内置固定3‑5道情景题；

- Commercial‑V1支持后台题库管理，可增删题目，支持题目标签（探索类/风险决策类/冲突处理类）。

3. 答题会话管理：中途退出可以续答；作答全部原始文本完整落库，原始作答属于用户私有数据资产。

4. 提交之后，调用【AI能力解析模型】中台，解析全部回答，输出：8维能力分数0‑100、认知风格标签集合、21席初始化得分。

5. 生成初始化航行护照快照；生成测试报告页面可视化雷达图。

6. 隐私：用户可以选择是否把本次测试答卷用于后续系统迭代优化；默认为不授权。

7. MVP内置演示模式：一键加载预置User‑Alpha / User‑Beta两套脱敏模拟答卷，直接生成两套航行档案，用于路演对照，不需要手动答题。

 

MVP✅实现，Commercial‑V1增强

 

- 增强：多轮动态情景测试；ASR语音作答（用户口述回答，语音转文字）；题库版本A/B测试。

 

非功能

 

- 原始答卷加密存储；访问必须鉴权。

 

System‑02：AI能力模型系统（中台核心，见第07章节完整定义）

 

定位：对用户文本作答、Mission协作反馈，做结构化解析；输出8维能力向量、认知风格、21席席位打分；提供可解释依据。

包含Prompt模板库、向量计算、分数迭代更新逻辑、可解释溯源。

 

System‑03：21席灵魂协作系统

 

定位：定义21席三舱全部规则、席位权重、席位依赖关系、席位胜任度打分规则；21席是认知职能，不是职业岗位。

 

核心业务规则完整定义

 

三大舱，每舱7席，合计21席；完整席位定义：

 

A舱｜探索舱 Discover（使命回答：我们应该去哪里？）

 

1. 探索者 Explorer：发现未知问题、新现象、新可能性

2. 发现者 Discoverer：搜集线索，识别潜在机会与信号

3. 观察者 Observer：客观观察现象，记录事实，不带预设判断

4. 研究者 Researcher：调研、查证资料，建立事实基础

5. 想象者 Imaginator：发散想象，生成多种未来可能性

6. 提案者 Proposer：把想法整理成可被讨论的正式提案

7. 连接者 Connector：跨领域关联信息，建立人和想法之间的连接

 

B舱｜建造舱 Build（使命回答：如何把想法变成可抵达的路线）

 

1. 指引者 Director：对齐使命目标，确立原则与边界

2. 战略师 Strategist：构建高层路径、全局策略

3. 架构师 Architect：搭建系统架构、整体结构

4. 拆解师 Decomposer：把大使命拆解为可执行任务单元

5. 设计师 Designer：设计方案、产出形态与体验

6. 工程师 Engineer：把方案转化为可运行产物

7. 执行者 Executor：落地执行具体任务，交付产出物

 

C舱｜治理舱 Govern（使命回答：确保抵达目的地时，仍然是我们想要成为的文明）

 

1. 导航者 Navigator：监控航向，对照目标判断是否偏离

2. 决策者 Decider：面对不确定性，做出关键取舍与最终选择

3. 监督者 Supervisor：监控过程进度，识别偏差

4. 风险官 Risk‑Officer：识别潜在风险，评估风险等级

5. 审核者 Auditor：核验产出证据，检查交付物是否达标

6. 仲裁者 Arbitrator：处理团队内部冲突、观点分歧

7. 守门者 Gate‑Keeper：守住使命底线、价值原则，拦截偏离核心价值的方案

 

21席系统业务规则

 

1. 每一个舰员，对21个席位，都拥有0‑100的胜任度分数；分数来自两部分加权：

- 权重30%：登舰测试初始化得分

- 权重70%：历次真实Mission协作反馈回填迭代得分（护城河主要来源）

 

重要：初始化测试只占30%权重；越多次航行，历史协作行为占比越高。

2. 一个Mission舰队21席是职能全集，不等于强制21个真人；允许一个真人兼任多个席位。

3. 硬约束（系统强制校验）：治理舱三个高风险席位【决策者、风险官、守门人】不能由舰载智能Agent承担，必须分配真人舰员；其余席位可以允许Agent临时补位，但是Agent补位会在系统标记【Agent临时补位风险】，组舰算法给出红色风险提示。

4. 每一个Mission发起的时候，指挥官需要勾选：本Mission必须保证哪些席位必须真人；组舰算法把这个作为硬约束条件。

5. 席位胜任分数必须支持可解释溯源：点开席位分数，可以看到：该分数来自哪几次登舰测试回答，哪几次Mission的协作反馈，每一条依据来源。（答辩评委重点关注“可解释AI”）

 

MVP✅实现；Commercial‑V1增强

 

- MVP：完整21席定义、分数加权计算、可解释溯源基础、硬约束校验；演示模式预置两套Alpha/Beta完整21席分数。

- 商业增强：席位之间依赖关系图谱；跨席位协作冲突风险模型。

 

System‑04：AI组舰算法 Fleet‑Formation系统

 

定位：输入Mission需求约束 + 候选池全部人员的私有航行档案；输出最优舰队推荐方案；输出匹配依据、风险清单；支持人工调整。

 

算法业务逻辑（MVP实现简化启发式算法，不做重型整数规划；商业V1可以升级运筹优化）

 

输入参数

 

1. Mission对象：Mission目标描述；必须真人的席位集合；Mission类型；任务周期；约束条件。

2. 候选人员集合：每一个候选者完整航行档案：8维能力向量、全部21席胜任分数、认知风格标签、历史Mission履历。

 

优化目标（最大化）

 

1. 21席职能覆盖度：尽可能补齐全部21席；重点保障强制真人席位。

2. 能力互补：降低舰队内部席位胜任度高度重叠；同一席位不要多个人高分冗余；不同席位之间补齐短板。

3. 认知多样性：舰队认知风格标签多元化，避免全部是同一种思维模式。

4. 历史协作正向记录：优先选择历史同类型Mission中反馈表现优秀的舰员。

5. 人机平衡：尽可能减少Agent临时补位席位数量。

 

约束条件（硬约束，不满足则输出告警，不生成方案）

 

1. 所有标记【必须真人】的治理舱席位，必须分配真人，不能Agent补位。

2. 同一个舰员，可以分配多个席位；但设置上限，单人最多兼任N席（MVP上限5席，可配置），防止一个人承担全部职能。

 

输出结果

 

1. 舰队推荐方案：舰队编号；每一个21席分配的舰员；标记哪些席位是真人、哪些是Agent临时补位。

2. 匹配解释报告：为什么该人员被分配这个席位；溯源到该舰员航行档案中的哪一条证据（哪次测试、哪次Mission反馈）。

3. 风险清单：哪些关键席位缺失、哪些人员兼任过多席位、哪些认知风格高度同质化、哪些席位由Agent临时补位。

4. 给出多套备选方案（MVP输出1套主方案 + 1套备选；商业多套）。

 

交互规则

 

1. 算法输出全部是建议；指挥官可以自由增删人员，手动修改席位分配。

6.1 航行档案Expedition‑Passport时序版本规则（重中之重，赛道护城河）

 

1. 用户每一次【初始化生成】、每一次【Mission完成反馈回填】，系统都会生成一份完整航行档案快照版本；版本号自增， passport_version_id 唯一主键。

3. 21席席位分数计算公式：

 

 席位最终得分 = 初始化登舰测试得分 × 0.3 + Σ（历次Mission该席位协作反馈得分 × 权重系数） ×0.7 

单次Mission反馈权重系数：同一个用户，参与Mission越多，历史Mission的权重做时间衰减，最近Mission权重更高。

 

4. 数据权限规则：

- 用户本人：可以查看自己全部版本快照、原始登舰答卷、全部反馈记录。

- 平台超级管理员：可以查看脱敏统计；业务原始私有数据，必须用户授权才可以访问，管理员禁止直接读取原始答卷。

 

6.2 Mission七步闭环流转规则

 

节点顺序固定： 提出 → 指引 → 拆解 → 执行 → 监督 → 决策 → 审核 

 

1. 每一个节点完成条件：提交本阶段产出物；本阶段对应负责席位舰员确认完成。

2. 【决策】节点强制约束：必须由分配到治理舱【决策者】真人舰员手动点击确认；舰载智能Agent输出只能作为参考，不能流转状态。

4. 流转不允许跳节点；必须顺序执行。

4. 重要安全：Agent禁止读取用户原始登舰答卷，输入上下文只传入结构化分数，不传原始敏感文本。

 

7.5 向量数据库（Commercial‑V1；MVP可以不用向量库，预留接口）

 

商业版本，把用户作答、Mission产出做向量化，用于候选池语义检索；MVP为了48小时开发，不引入向量数据库，仅结构化字段；代码预留接入点。

8.2 数据库安全强制要求

 

1. 用户原始登舰答卷 user_answer_raw_list 字段必须字段级加密存储；数据库存储密文；应用层内存解密；数据库本身不能直接读取明文。

2. 航行档案快照业务数据禁止物理删除，全部软删除 deleted_at ；

3. 所有数据库访问，应用层必须做鉴权；不能仅仅依靠前端页面隐藏做权限控制；后端API每一次读取私有航行档案，必须校验用户访问授权。

4. 禁止日志打印原始用户答卷明文；防止日志泄露私有数据。

10 游戏化界面交互 & NPC语音TTS、ASR对话系统

 

⚠️MVP‑hackathon分支：不做完整NPC对话系统；只做1个TTS样例Demo：首页星舰领航员NPC简短语音播报世界观文案，作为能力样例；不做完整会话对话；完整NPC对话、多轮交互、ASR语音输入全部放在Commercial‑V1分支。

 

10.1 Commercial‑V1完整游戏化交互需求

 

1. NPC角色：星舰领航员Navigator‑NPC；产品世界观的虚拟星舰领航员。

2. 交互入口：

- 全局悬浮NPC头像按钮，任何页面均可唤起对话面板；

- 首次登录登舰流程，NPC主动弹窗引导用户完成登舰测试；

- 舰桥工作台右侧，可切换「Agent集群面板 / NPC领航员对话面板」。

3. NPC能力清单：

1）世界观科普：讲解21席、三舱、Mission闭环、航行护照规则；

2）流程引导：新用户一步步指引完成申请登舰→答题→查看航行护照；

3）状态播报：Mission阶段变更、舰队组建完成、收到新的Mission通知，NPC语音+文字双播报；

4）辅助调用舰载智能Agent：自然语言对话，由NPC调度后端各个Agent集群；用户不需要手动点选Agent卡片，直接对话下达指令；

5）成就播报：用户升级称号、获得星标，NPC触发祝贺语音动画；

4. 多媒体能力

- TTS文本转语音：支持多种音色；领航员固定使用沉稳星际领航音色；

- ASR语音识别：用户可以直接语音说话，转成文本输入对话；登舰测试支持口述作答；

- 动画：NPC头像微动画（眨眼、点头），对话气泡，星舰粒子特效；

5. 业务硬约束：

 

NPC只是人机交互外壳；底层依旧调用原有Agent中台；NPC绝不可以绕过“人类确认拦截器”，所有Agent生成的业务建议，仍然需要真人点击确认，才会改变Mission业务状态。NPC只做表达层，不拥有业务决策权。

 

10.2 MVP‑hackathon TTS最小样例实现范围

 

1. 仅首页世界观页面；增加领航员NPC悬浮头像；点击头像，调用TTS接口朗读一段Slogan文案；

12 接口概要设计（RESTful API，关键核心接口清单）

 

完整OpenAPI文档由FastAPI自动生成，访问 /docs 即可查看；下面列出业务核心接口，便于前后端对齐开发。

鉴权规则：绝大多数接口请求头携带 Authorization: Bearer {jwt_token} ；公开首页、注册登录接口无需token。

 

12.1 鉴权模块  /api/v1/auth 

 

1.  POST /api/v1/auth/register  用户注册，生成地球文明编号 civilization_no 

2.  POST /api/v1/auth/login  登录获取JWT Token

3.  GET /api/v1/auth/me  获取当前登录用户基础信息

 

12.2 登舰测试系统  /api/v1/expedition‑test 

 

1.  GET /api/v1/expedition‑test/question‑list  获取测试情景题目列表（MVP固定3‑5道）

2.  POST /api/v1/expedition‑test/session/create  创建测试会话test_session_id

3.  PUT /api/v1/expedition‑test/session/{session_id}/submit‑answers  提交用户全部原始作答文本

4.  POST /api/v1/expedition‑test/session/{session_id}/parse  触发后端调用LLM解析答卷，生成初始化航行档案快照

5.  GET /api/v1/expedition‑test/session/{session_id}/report  获取解析完成测试报告（8维向量、认知标签、初始化21席得分）

6.  【演示模式专用】POST /api/v1/expedition‑test/demo/preset‑alpha  一键载入预置User‑Alpha模拟答卷生成快照

7.  【演示模式专用】POST /api/v1/expedition‑test/demo/preset‑beta  一键载入预置User‑Beta模拟答卷生成快照

 

12.3 航行护照（航行档案快照）  /api/v1/passport 

 

1.  GET /api/v1/passport/latest  获取当前用户最新版本航行档案快照

2.  GET /api/v1/passport/history‑versions  获取该用户全部历史快照版本列表（版本回溯）

3.  GET /api/v1/passport/snapshot/{snapshot_id}  根据快照ID获取某一版完整档案

4.  POST /api/v1/passport/export‑my‑all‑data  用户导出自己全部私有数据（隐私合规）

5.  PATCH /api/v1/passport/privacy‑setting  更新隐私授权配置

 

12.4 候选池  /api/v1/candidate‑pool 

 

1.  GET /api/v1/candidate‑pool/list  获取候选池人员列表（返回脱敏航行护照摘要：称号、星标、TOP3席位；完整分数需要授权才返回）

2.  POST /api/v1/candidate‑pool/add‑me  将本人加入公共候选池

 

12.5 Mission航行使命  /api/v1/mission 

 

1.  POST /api/v1/mission/create  创建新Mission

2.  GET /api/v1/mission/my‑list  我发起的/我参与的Mission列表

3.  GET /api/v1/mission/{mission_id}/detail  Mission详情

4.  PATCH /api/v1/mission/{mission_id}/update‑status  更新Mission状态（受后端状态机校验，不能随意跳转阶段）

5.  POST /api/v1/mission/{mission_id}/close‑prepare  Mission进入收尾，开启协作反馈表单

 

12.6 AI组舰算法核心接口  /api/v1/fleet‑formation （路演对照演示核心）

 

1.  POST /api/v1/fleet‑formation/calc‑recommend 

 

请求入参：mission_id、候选人员user_id数组；触发后端组舰算法；返回推荐舰队方案、风险清单、匹配解释报告。

 

2.  POST /api/v1/fleet‑formation/demo/re‑calc‑swap‑user 

 

✨路演演示模式专属接口：替换候选池内指定user_id（Alpha ↔ Beta），其余入参完全不变，重新运行组舰，直接返回新舰队结果。前端页面一个按钮调用此接口，完成赛道强制对照演示。

 

3.  POST /api/v1/fleet‑formation/confirm‑fleet  指挥官确认舰队，写入fleet数据库，生成舰队编号NW‑F‑XXXX；后端执行硬约束校验（治理舱真人强制校验）；校验失败返回风险，不允许确认。

4.  PUT /api/v1/fleet‑formation/{fleet_id}/manual‑adjust  指挥官手动调整席位分配；提交之后后端重新计算风险清单返回前端。

 

12.7 舰队舰桥工作台 & Mission阶段产出  /api/v1/fleet‑deck 

 

1.  GET /api/v1/fleet‑deck/{fleet_id}/overview  获取舰队总览、21席分配、当前Mission阶段

2.  POST /api/v1/fleet‑deck/{fleet_id}/phase‑output/submit  提交某一Mission阶段产出物

3.  POST /api/v1/fleet‑deck/{fleet_id}/phase‑output/{output_id}/confirm  本阶段产出确认完成；决策节点会做后端强制校验：操作人必须是分配的【决策者】真人账号，否则返回403拒绝流转状态。

 

12.8 舰载智能Agent集群  /api/v1/ship‑intelligence 

 

1.  POST /api/v1/ship‑intelligence/agent/call 

 

入参：mission_id、fleet_id、agent_name（Research‑Agent / Decomposition‑Agent / Risk‑Agent / Audit‑Agent）、用户指令文本；

后端逻辑：自动装配上下文（Mission目标、已有阶段产出），调用对应Agent Prompt模板，请求大模型；完整记录agent_call_log日志；返回Agent输出文本。

⚠️重要：该接口只返回Agent文本建议；绝对不会修改任何Mission/fleet业务状态；业务状态变更，必须走上面phase‑output/confirm人类确认接口。强制拦截器在后端生效，前端无法绕过。

 

2.  GET /api/v1/ship‑intelligence/agent‑call‑log/list  获取本舰队全部Agent调用历史日志，用于Innovate Trace航迹导出。

 

12.9 Mission协作反馈 & 航行档案回填  /api/v1/mission‑feedback 

 

1.  POST /api/v1/mission‑feedback/submit  Mission收尾，提交协作结构化反馈表单

2.  POST /api/v1/mission‑feedback/{mission_id}/trigger‑passport‑iteration 

 

全部反馈收集完成后，触发后端航行档案快照迭代计算；生成每一位舰员全新passport_snapshot_id快照版本；旧快照记录永远保留不覆盖。

 

12.10 报告&导出接口（比赛提交关键）  /api/v1/report 

 

1.  GET /api/v1/report/mission‑archive/{mission_id}/full‑report  获取Mission完整航行报告JSON

2.  POST /api/v1/report/export‑innovate‑trace  导出Innovate Trace航迹文档（JSON/PDF二选一，直接匹配选手手册要求的四条航迹：问题、数据、验证、迭代）

3.  POST /api/v1/report/export‑mission‑pdf  导出完整Mission航行报告PDF。

 

12.11 MVP极简超级管理员后台接口  /api/v1/admin/simple 

 

commercial‑v1完整运营后台会扩展更多接口；MVP仅最小集合：

 

1.  GET /api/v1/admin/simple/demo‑preset/list  查看预置Alpha/Beta演示数据集

3.  GET /api/v1/admin/simple/global‑llm‑call‑stat  查看大模型调用统计、token消耗，用于调试。

14 部署架构、环境配置、CI/CD

 

14.1 mvp‑hackathon｜魔搭创空间部署（比赛唯一正式部署环境）

 

参考中客松选手手册提交要求：作品必须部署魔搭创空间，路演时刻保持Running状态。

 

环境规格建议（魔搭创空间容器）

 

- 容器镜像：Python 3.11；

- 资源：2核4G内存；不需要GPU；全部大模型调用走外部推理API（魔搭ModelScope推理服务 / OpenAI兼容接口），不在本地容器部署大模型，节省算力资源。

- 容器内部运行：FastAPI后端服务 + Vue3前端Web静态资源（可以用uvicorn挂载静态前端dist产物，或者使用简单nginx；魔搭创空间支持端口暴露）。

- 数据库方案：

方案A（比赛Demo最简单）：MVP开发与演示阶段使用SQLite文件数据库，降低部署难度；⚠️注意：SQLite仅用于Demo演示；并发弱，商业版本必须切换PostgreSQL。

方案B：魔搭创空间挂载外部PostgreSQL实例（如果可以开通云数据库）。

 

📌开发给AtomCode的重要说明：代码中数据库连接做配置开关； .env 文件中 DB_ENGINE=sqlite 为演示模式； DB_ENGINE=postgresql 商业版本。Demo使用SQLite，省去容器安装PostgreSQL的繁琐，保障48小时部署成功。

但是数据库的表结构、字段、ORM模型完全按照PostgreSQL设计；切换数据库引擎，业务代码不需要改动。

 

魔搭创空间部署步骤文档  deploy/modelscope‑deploy.md （写进仓库，方便参赛同学部署）

 

1. 仓库代码上传魔搭创空间；

2. 构建环境：安装requirements.txt全部python依赖；前端web执行 npm install && npm run build ，产出dist静态文件夹；

3. 配置.env环境变量：

- 填入魔搭ModelScope大模型推理API密钥（OpenAI兼容格式）；

- 设置 MOCK_DEMO_MODE=true 开启演示模式；

- 设置 DB_ENGINE=sqlite ；

4. 执行数据库初始化： alembic upgrade head ；

5. 运行预置demo数据集脚本： python scripts/init‑demo‑preset‑snapshot.py ；生成Alpha/Beta两套模拟档案；

6. 启动服务： uvicorn app.main:app --host 0.0.0.0 --port 7860 ；魔搭创空间暴露7860端口；

7. 访问对外链接，确认页面全部功能可用；完整跑一遍13章节Demo全流程；确认Demo对照实验可以正常运行；确认导出PDF、Innovate Trace文档功能正常；

⚠️风险降级预案（魔搭容器崩溃）

17.3 Innovate Trace 四条航迹完整成文（直接导出，比赛提交）

 

对应选手手册07章节BUILD & EVIDENCE要求，四条航迹：问题、数据、验证、迭代。

 

航迹1｜问题

 

当下创新项目、黑客松、开源协作的组队方式高度依赖简历、自我技能标签；简历是人的自我美化描述，无法表征参与者真实的认知模式、风险偏好、历史协作表现。很多创新项目技术人员齐全，但完成复杂使命所必须的认知职能席位出现缺失，导致项目中途失败，大量人力成本沉没。

我们的目标用户：复杂创新使命的发起者、创新项目参与者、开源与社会创新协作人员。

本项目希望解决：如何基于人真实的协作行为数据，而不是自我简历，完成复杂使命的人机互补编组；构建一套“未定信号”产品：产品输出高度依附用户独有的持续积累的私有航行档案。

 

航迹2｜数据

 

本产品独有私有数据资产为用户航行档案Expedition Passport；由两部分组成：

1）初始化输入：登舰测试的用户开放式情景作答原始文本，记录用户面对危机情景的真实推理路径、风险选择；

2）核心护城河来源：每一次Mission航行使命完成之后回填的协作反馈记录；记录该舰员在21个认知席位上的真实产出、协作表现、风险事件；该数据属于用户个体独有，外部无法获取；每一次反馈都会生成航行档案全新版本快照，旧版本永久保留，不覆盖。

Demo演示阶段，全部使用人工构造脱敏模拟航行档案数据集User‑Alpha、User‑Beta；两套档案认知特征完全相反；用于完成赛道强制对照演示；没有使用任何真实自然人隐私数据。

产品核心个体差异验证：同一Mission、同一候选池，仅仅替换一份用户私有航行档案，AI组舰输出的舰队席位分配会发生实质性改变。

两条“去掉测试”：①去掉私有航行档案，系统退化为通用情景问卷，无法生成个性化21席画像与定制化舰队编组；②去掉AI舰载智能，人工解析几十位候选者开放式文本、做多维度能力评估、互补舰队编组，人力成本极高，无法规模化。

 

航迹3｜验证

 

我们开展多轮内部模拟验证：

 

1. 数据集对照验证：预置两套完全相反的脱敏模拟航行档案Alpha与Beta；固定Mission与其余候选人员；运行组舰算法；确认替换用户档案之后舰队分配发生实质差异；满足未定信号赛道个体差异的演示要求。

2. 业务规则验证：单元测试校验治理舱【决策者、风险官、守门人】强制真人硬约束；当候选池无法提供真人，组舰算法输出致命风险告警，不允许确认舰队。

3. 人机边界验证：反复测试Agent调用链路；确认Agent输出只能给出建议；Mission业务状态流转必须真人确认；Agent永远无法自动推进Mission闭环，贯彻“AI加速航行，人类决定航向”的产品原则。

4. 退化场景验证：模拟移除全部Mission回填的协作反馈，仅仅保留初始化登舰答卷；系统能力退化为普通情景测试，无法产出高可信度的协作编组建议，验证产品护城河来自持续积累的航行档案。

5. 流程全链路验证：完整跑通Demo全链路：申请登舰→生成航行档案→AI组舰对照实验→舰桥Mission七步闭环→Mission收尾反馈回填生成新版本航行档案→导出Innovate Trace航迹文档。

 

航迹4｜迭代

 

项目早期原始构想：一个面向创新人才的招聘/求职匹配平台。

第一轮迭代：根据未定信号赛道命题，剥离求职招聘的业务语境；意识到单纯简历匹配不具备护城河；产品定位从“人才招聘平台”转向“复杂创新使命的人机协作编组系统”。

第二轮迭代：发现“一次性问卷测试”不具备真正护城河；问卷仅仅是初始化；将产品核心壁垒重新定义为Mission任务完成后持续回填迭代的私有航行档案快照；调整21席分数权重：登舰测试初始化仅占30%权重，70%权重来自真实历史协作反馈。

第三轮迭代：确立人机边界硬规则；AI舰载智能只能做辅助建议；关键使命决策、Mission状态流转必须真人确认；增加后端全局“人类确认拦截器”，从底层防止Agent越权执行业务变更。

第四轮迭代：区分MVP‑hackathon比赛版本与commercial‑v1商业版本；把宏大的APU生产力凭证、新大陆经济实验室降级为远期V2.0构想；MVP只聚焦完成赛道必须的核心闭环；避免Demo概念空洞无法落地。

第五轮迭代：针对黑客松48小时开发与现场演示风险，设计演示模式；预置两套脱敏模拟航行档案；赛道硬性对照实验不依赖现场实时大模型推理，提升路演演示稳定性；同时完善全套降级预案。

后续迭代规划（V2.0商业版本）：完善大规模候选池优化算法；完整NPC‑TTS‑ASR游戏化交互；多租户组织中台；APU生产力单元完整业务；扩展更多Agent；接入向量数据库，支持语义检索候选池。

附录C：AI组舰启发式算法完整伪代码（直接给到AtomCode翻译成Python，MVP版本）

 

文件路径： backend/app/core/fleet_formation/fleet_heuristic_algorithm.py 

⚠️ MVP是启发式加权打分；不做整数规划、遗传算法；商业V1再升级复杂优化。

 

python  

"""

MVP‑hackathon 启发式组舰算法

输入：

    mission: Mission对象，包含目标、必须真人席位集合

    candidate_user_list: List[UserWithPassportSnapshot]

        每一个候选者携带【最新航行档案快照】：21席分数、8维向量、认知风格标签、历史mission履历

输出：

    FleetRecommendResult:

        - seat_assignment_list：21席分配方案（human/agent_temp）

        - explain_report：匹配解释报告

        - risk_list：风险告警清单（致命风险/橙色警告）

        - alternative_plan：一套备选方案

"""



def fleet_formation_heuristic(mission, candidate_user_list):

    risk_list = []

    explain_report = []

    seat_assignment = dict() # key:席位名 value:分配对象{type,user_id/agent_name,reason}



    must_human_seats = mission.must_human_seats # Mission勾选必须真人的席位

    # 硬约束1：治理舱强制真人三席位，无条件加入must_human_seats

    for seat in MUST_HUMAN_GOVERN_SEATS:

        if seat not in must_human_seats:

            must_human_seats.append(seat)



    all_seats = ALL_21_SEATS.copy()

    remaining_candidates = candidate_user_list.copy()



    # -------- 第一步：优先分配【必须真人】的席位（优先级最高，致命约束） --------

    for seat in must_human_seats:

        # 对该席位，所有候选者计算适配分 = 该席位seat_full_score

        candidate_score_pair = []

        for user in remaining_candidates:

            score = user.passport_snapshot.seat_full_score[seat]

            candidate_score_pair.append( (score, user) )

        # 从高到低排序

        candidate_score_pair.sort(reverse=True, key=lambda x:x[0])



        best_score, best_user = candidate_score_pair[0]

        if best_score < 40:

            # 致命风险：没有合适真人满足强制真人席位，方案不可确认

            risk_list.append({

                "risk_level":"FATAL",

                "seat":seat,

                "desc":f"强制真人席位【{seat}】，全部候选者胜任分数低于40，无合适真人候选，舰队方案无法确认。"

            })

            seat_assignment[seat] = {"assign_type":"agent_temp","agent_alias":"Risk‑Agent","reason":"致命风险，无真人候选"}

            continue



        # 分配该席位给best_user

        seat_assignment[seat] = {

            "assign_type":"human",

            "assigned_user_id": best_user.user_id,

            "reason":f"该席位最高分候选者，席位得分{best_score}，来自航行档案快照版本{best_user.passport_snapshot.passport_version_no}"

        }

        explain_report.append({"seat":seat,"user_id":best_user.user_id,"reason":seat_assignment[seat]["reason"]})



        # 统计该用户已经被分配多少席位

        user_assign_count = sum([1 for s in seat_assignment.values() if s.get("assigned_user_id") == best_user.user_id])

        if user_assign_count >= MAX_DOUBLE_SEAT_PER_USER:

            risk_list.append({

                "risk_level":"WARNING_ORANGE",

                "seat":seat,

                "user_id":best_user.user_id,

                "desc":f"舰员{best_user.civilization_no}已经兼任{user_assign_count}个席位，超过上限{MAX_DOUBLE_SEAT_PER_USER}，存在过载风险。指挥官可以手动调整。"

            })



    # --------第二步：分配剩余非强制真人席位 --------

    for seat in all_seats:

        if seat in seat_assignment:

            continue #已经分配过，跳过

        # 候选打分，优先选还没有被大量分配席位的人；席位原始得分*0.7 + （未被分配权重加分0‑30）

        candidate_score_pair = []

        for user in remaining_candidates:

            base_seat_score = user.passport_snapshot.seat_full_score[seat]

            assigned_count_for_user = sum([1 for s in seat_assignment.values() if s.get("assigned_user_id") == user.user_id])

            overload_penalty = assigned_count_for_user * 6 #兼任越多，扣分越大

            final_score = max(0, base_seat_score - overload_penalty)

            candidate_score_pair.append((final_score, base_seat_score, user))



        candidate_score_pair.sort(reverse=True, key=lambda x:x[0])

        best_final_score, best_raw_score, best_user = candidate_score_pair[0]



        if best_final_score >=35:

            # 分配真人

            seat_assignment[seat] = {

                "assign_type":"human",

                "assigned_user_id":best_user.user_id,

                "reason":f"席位综合匹配分{best_final_score}，原始席位得分{best_raw_score}"

            }

            explain_report.append({"seat":seat,"user_id":best_user.user_id,"reason":seat_assignment[seat]["reason"]})

            # 兼任计数与橙色告警

            user_assign_count = sum([1 for s in seat_assignment.values() if s.get("assigned_user_id") == best_user.user_id])

            if user_assign_count >= MAX_DOUBLE_SEAT_PER_USER:

                risk_list.append({

                    "risk_level":"WARNING_ORANGE",

                    "seat":seat,

                    "user_id":best_user.user_id,

                    "desc":f"舰员{best_user.civilization_no}已经兼任{user_assign_count}个席位，超过上限{MAX_DOUBLE_SEAT_PER_USER}，存在过载风险。指挥官可以手动调整。"

                })

        else:

            # 分数不足，Agent临时补位；标记黄色风险

            seat_assignment[seat] = {

                "assign_type":"agent_temp",

                "agent_alias":map_seat_to_agent(seat), #席位映射对应Agent

                "reason":f"无合适真人候选，由Agent临时补位，该席位建议指挥官后续手动补充真人。"

            }

            risk_list.append({

                "risk_level":"WARNING_YELLOW",

                "seat":seat,

                "desc":f"席位【{seat}】由Agent临时补位，建议补充真人舰员。"

            })



    # --------第三步：认知多样性校验，追加风险提示（不阻断方案，仅告警） --------

    # 提取已经分配真人的全部舰员认知风格标签集合，判断是否高度同质化

    assigned_real_user_ids = set()

    for item in seat_assignment.values():

        if item["assign_type"] == "human":

            assigned_real_user_ids.add(item["assigned_user_id"])

    user_objects = [u for u in candidate_user_list if u.user_id in assigned_real_user_ids]

    style_list = []

    for u in user_objects:

        style_list.extend(u.passport_snapshot.cognitive_style_tags)

    unique_style = set(style_list)

    if len(unique_style) <=3:

        risk_list.append({

            "risk_level":"WARNING_YELLOW",

            "seat":"全局舰队",

            "desc":f"舰队认知风格集合仅有{len(unique_style)}类，认知多样性偏低，容易出现思维盲区，建议指挥官手动调整部分人员。"

        })



    # --------第四步：生成备选简单方案（MVP仅一套备选，商业版多套） --------

    alternative_plan = generate_alternative_plan(mission, candidate_user_list, seat_assignment)



    return FleetRecommendResult(

        seat_assignment_list=seat_assignment,

        explain_report=explain_report,

        risk_list=risk_list,

        alternative_plan=alternative_plan

    )

 

 

配套说明：

 

1.  map_seat_to_agent(seat) ：席位映射Agent，例如拆解师 → Decomposition‑Agent；风险官→Risk‑Agent；

2. 返回结果的risk_level枚举： FATAL 致命风险（舰队不能直接确认）； WARNING_ORANGE 橙色警告； WARNING_YELLOW 黄色提示；

3. 业务规则：哪怕存在FATAL致命风险，算法依然输出完整方案，但API返回标记 is_confirmable=False ，前端页面按钮【确认舰队】置灰不可点击；指挥官手动调整消除致命风险之后，按钮才启用。

4. 指挥官可以无视全部告警，手动强行修改分配，但致命风险不消除无法确认舰队；橙色、黄色告警可以无视直接确认。

Score_{dim\_init}=LLM\_output\_eight\_dim\_score

 

2）Mission反馈回填增量迭代（生成新版本快照）

 

权重规则：

 

- 初始化登舰测试：总权重 30%

- 全部历史Mission协作反馈总和：总权重 70%

- 历史Mission时间衰减：越近完成的Mission权重越高，更早的Mission逐步衰减，但不会归零。

def calc_new_passport_snapshot(old_snapshot, mission_feedback_delta_list):

    """

    old_snapshot：用户上一版航行档案快照（历史版本，只读，绝不修改）

    mission_feedback_delta_list：多次Mission反馈增量集合，每一条包含seat_delta、eight_dim_delta、mission_finish_time

    return：全新生成的passport_snapshot对象，全新version_no；old_snapshot完整保留在数据库。

    """

    # 时间衰减系数，最近Mission系数1.0；每往前推一个Mission，衰减0.85；最小不低于0.2

    sorted_feedback = sorted(mission_feedback_delta_list,key=lambda x:x["mission_finish_time"],reverse=True)

    weighted_seat_total = defaultdict(float)

    weighted_dim_total = defaultdict(float)

    total_weight_sum = 0.0

    decay_factor = 1.0



    for feedback in sorted_feedback:

        decay_factor = max(0.2, decay_factor * 0.85)

        total_weight_sum += decay_factor

        for seat_name,delta in feedback["seat_delta"].items():

            weighted_seat_total[seat_name] += delta * decay_factor

        for dim_name,delta in feedback["eight_dim_delta"].items():

            weighted_dim_total[dim_name] += delta * decay_factor



    # 基线 = 旧快照的席位分数

    new_seat_score = dict()

    new_dim_score = dict()

    for seat in ALL_21_SEATS:

        history_feedback_contribution = weighted_seat_total[seat] / total_weight_sum if total_weight_sum>0 else 0

        new_seat_score[seat] = clamp(

            old_snapshot.seat_full_score[seat] * 0.3 + history_feedback_contribution * 0.7,

            0,

            100

        )

    for dim in EIGHT_DIM_KEYS:

        history_feedback_contribution = weighted_dim_total[dim] / total_weight_sum if total_weight_sum>0 else 0

        new_dim_score[dim] = clamp(

            old_snapshot.eight_dim_score[dim] *0.3 + history_feedback_contribution *0.7,

            0,

            100

        )

    # clamp函数：限制数值在0‑100区间，防止越界

    return build_new_snapshot_object(old_snapshot,new_seat_score,new_dim_score,feedback_delta_list)

 

 

⚠️业务硬性约束：

 

1. old_snapshot绝对不能update修改；只读取，生成全新记录插入数据库。

2. clamp 强制把分数锁死0‑100，防止多次反馈叠加溢出。

3. 每一次迭代生成新 passport_version_no 版本号+1；溯源字段 snapshot_source_type="mission_feedback" ， source_relation_id=本次mission_id 。
